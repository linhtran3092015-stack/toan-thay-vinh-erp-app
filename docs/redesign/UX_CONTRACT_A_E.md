# UX contract: Phases A–E

## Contract rules

This is an inventory of operations verified in the current repository, not a proposal for new capabilities. “Role / capability” deliberately names an existing permission capability rather than inventing a business role. Confirmation wording, action availability, validation, permission checks, Server Action bindings, RPC bindings, and audit semantics remain feature-owned.

`locked` is represented by a session `lockedAt` value; it is not an additional `SessionStatus` enum value in the current TypeScript model.

## Known contract ambiguity

- The TypeScript session-generation actions authenticate a user but do not perform an explicit `requirePermission` call. The applicable permission is enforced by the existing RPC/database contract or surrounding UI. Wave 5 must preserve that exact behavior and must not assign a new permission code without a separate audit.
- A database corrective path named `reset_unlocked_class_session_before_start` exists in migrations, but no active frontend binding was found in the A–E surfaces. It is intentionally not a redesign action.
- The repository contains feature-specific confirmation surfaces, but this Wave 0 inventory does not normalize their wording. Later waves must retain the existing feature-owned meaning and copy rather than infer a generic policy.
